OPL Cloud：Workspace SSOT 迁移图

这页解释 Customer 与 Admin 如何组合 Workspace、Fabric 和 Serve 的独立事实。当前实现、验证证据与未完成验收分别链接其权威文档。

解释性导航
不记录分支进度或运行时验收
阅读方式：图中说明事实来源与调用方向。架构拥有领域分工；实现架构说明实际入口；status保存验证证据；roadmap保存剩余验收。

1. 业务链：一个 Workspace，多个事实 owner

Customer / Admin 读

浏览器只选择入口和展示 source envelope，不拥有业务状态。

Cloud identity 走 /api/v2/*；legacy identity 才走保留的 /api/*。

→

Console BFF 组合

鉴权、调用 owner、校验身份和 scope，再组合多个独立事实。

不持久化 Workspace 状态，不把 CP 读失败当 fallback。

→

Workspace owner SSOT

Workspace identity、Tenant 引用、entitlement、生命周期、资源计划、resource set 引用。

Customer 列表/详情和 Cloud Admin Workspace 列表/详情都从这里读业务 DTO。

Fabric 物理事实

Compute / Storage / Attachment / Runtime 等 provider resource 的当前观察、绑定和删除读回。

不能决定 Workspace entitlement，也不能决定 Agent readiness。

→

Serve 应用事实

当前 deployment、current selection、runtime readiness、access route、application availability。

Admin 与 Customer 对“应用可用”应使用同一 Serve readback。

→

Ledger / Gateway 外部事实

Ledger：receipt、reconciliation、provenance。

Gateway/Sub2API：wallet、effective Key、Group、usage、routing。

2. 事实与权限的边界

Workspace
身份、Tenant、业务生命周期、资源计划和 resource set 引用。
不推断当前应用部署与入口。
Fabric
指定 Workspace/resource set 的物理资源观察。
资源存在不等于应用就绪。
Serve
当前 deployment、readiness 与 access metadata。
Admin 与 Customer 读取同一事实；分别采用平台 operator 与 Tenant 权限。
CloudIdentity
会话、角色、action、scope 和精确资源授权。
BFF 获取决定，各 owner 独立重验；应用自身登录不由只读权限授予。
Control Plane
保留对象和历史义务由原 owner 处理。
具体 caller 与退休条件见实现架构的保留链路清单。

3. 权威入口

API 与授权合同：各 owner action、权限和 scope。

Admin Workspace 实现链：当前 source 路径及消费者。

保留 writer/caller 清单：迁移源与现存义务。

验证证据与未完成验收：代码、CI、Candidate 与 Instance 各层事实。

4. 页面事实如何归因

Workspace 业务状态、Tenant、创建者、资源计划引用。

Fabric resource set、resource kind/state、provider reference、observation time、deletion/absence facts。

Serve deployment 选择、应用可用性和匹配该 deployment 的入口。

Unavailable 未由对应 owner 提供的字段保留不可用原因；不借用其他 owner 的字段填充。

5. 不应该做的事

不要：把 CP 的 Workspace projection 重新接成 Cloud Workspace fallback；把 Fabric 状态写进 Workspace；让 BFF 自己保存第二份 current status；因为 Candidate/Local qualification 成功就直接删除 CP；把 legacy 兼容路径和 Cloud 原生路径混成一个响应。

6. 判定顺序

已迁移/已验证边界或证据仍需补齐Control Plane 保留能力，需逐项清退BFF 只组合，不成为 owner
正确顺序：先识别事实 owner 与权限 → 读取对应 owner → 保持各层事实独立 → 区分源码、安装与运行时证据。具体迁移和验收只在权威文档维护。
