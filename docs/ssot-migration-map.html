先看结论：Cloud 原生 Workspace 的 Admin/Customer 主读路径已经统一到 Workspace owner；Fabric 负责物理资源现态，Serve 负责应用部署/可用性。Control Plane 仍是 legacy 和历史操作的保留 owner，不能直接整体删除。审计基线 ccab537 中，Admin 的 applicationAvailability 仍直接取 Workspace DTO；本分支已改为复用 Customer 的 Serve readback 组合逻辑。该源码修复尚未合并或完成 Instance 运行时采用验证。

1. 业务链：一个 Workspace，多个事实 owner

Customer / Admin 读

浏览器只选择入口和展示 source envelope，不拥有业务状态。

Cloud identity 走 /api/v2/*；legacy identity 才走保留的 /api/*。

→

Console BFF 组合

鉴权、调用 owner、校验身份和 scope，再组合多个独立事实。

不持久化 Workspace 状态，不把 CP 读失败当 fallback。

→

Workspace owner SSOT

Workspace identity、Tenant membership、entitlement、生命周期、资源计划、resource set 引用。

Customer 列表/详情和 Cloud Admin Workspace 列表/详情都从这里读业务 DTO。

Fabric 物理事实

Compute / Storage / Attachment / Runtime 等 provider resource 的当前观察、绑定和删除读回。

不能决定 Workspace entitlement，也不能决定 Agent readiness。

→

Serve 应用事实

当前 deployment、current selection、runtime readiness、access route、application availability。

Admin 与 Customer 对“应用可用”应使用同一 Serve readback。

→

Ledger / Gateway 外部事实

Ledger：receipt、reconciliation、provenance。

Gateway/Sub2API：wallet、effective Key、Group、usage、routing。

2. 现在的边界

Workspace lifecycle
已统一
Workspace owner 是业务状态 owner。
Admin 的生命周期字段应标记 source=workspace。
Current resources
已分离
Fabric 通过 Workspace 的 resourceSetId 做精确 readback。
不能用 CP 的历史 projection 替代 Fabric 当前观察。
Application availability
基线缺口；本分支源码已修
Admin 与 Customer 详情现复用同一 Serve readback 组合规则。
仍需 PR 当前 revision CI；合并后若要声明已安装，需由 Instance 对同一 Workspace 做 Admin/Customer 运行时比对。
Resource readiness
需澄清命名
Workspace 的 fulfillment/开通读回。
不是 Fabric 当前物理资源 condition，UI 不应把两者混成同一个实时状态。
Control Plane
保留迁移源
legacy identity、历史订单和未迁移能力仍使用。
不是 Cloud 原生 Workspace 的 fallback，也不是当前目标的第二 writer。

3. 还需要清什么

合入 Admin 的 Serve readback 修复

本分支已让 Admin BFF 复用 Customer 详情的 Serve 组合逻辑。Workspace 仍提供生命周期/履约事实；Serve 上游读失败保持 unknown，无部署/入口时按 Serve 规则返回 unavailable，不从 Workspace 字段兜底。

源码已改，待 CI/合并

把资源两个时间维度说清楚

保留 Workspace 的“开通/履约读回”和 Fabric 的“当前物理观察”，但在 DTO/UI 文案中区分名称，避免把历史 fulfillment 当作实时 provider 状态。

边界澄清

清退 legacy Workspace 执行链

逐项处理旧 Launch 的 recovery、renewal/expiry、delete/refund、旧应用部署/凭据/镜像维护。先盘点实际 callers、in-flight operations 和持久化 obligations，再删除 command、worker、config、adapter 与 exclusive tests。

需要迁移证据

迁移 Gateway / Account / wallet 旧能力

个人 Key、账户激活、管理员充值、旧 eligibility 和 recovery 仍有 Control Plane caller。它们不能被 Workspace 迁移顺手删除；要分别确认新 owner、caller withdrawal 和历史读者。

独立能力

清理 legacy pricing 与历史 Console 适配器

新 Workspace 走 Resource Catalog quote；旧 package pricing、账单、公告、ACK、identity transport 仍属于保留链。只有确认没有外部/已部署 caller 后，才能移除旧 wrapper 和专属测试。

独立能力

补齐部署与发布证据，不把它误当代码清退

当前 Candidate 构建已成功，但 exact-SHA PR CI、完整 P0 readiness、Instance 同 Candidate 部署验证仍未闭环。这是发布/安装验收，不等于 Control Plane 代码可以删除。

4. Admin 资源页当前会显示什么

Workspace 业务状态、Tenant、创建者、资源计划引用。

Fabric resource set、resource kind/state、provider reference、observation time、deletion/absence facts。

Unavailable 旧 Account/User 映射、receipt、Key usage、package/spec、zone、创建/过期时间等未由新 owner 提供的字段。

5. 不应该做的事

不要：把 CP 的 Workspace projection 重新接成 Cloud Workspace fallback；把 Fabric 状态写进 Workspace；让 BFF 自己保存第二份 current status；因为 Candidate/Local qualification 成功就直接删除 CP；把 legacy 兼容路径和 Cloud 原生路径混成一个响应。

6. 判定顺序

已迁移/已验证边界或证据仍需补齐Control Plane 保留能力，需逐项清退BFF 只组合，不成为 owner
正确顺序：先修 Admin 的 Serve readback 来源 → 再按 capability 盘点 CP callers、持久化 obligations 和外部部署流量 → 迁移真实 caller → 保留历史数据/回放读者 → 删除旧 writer/worker/config/test → 最后重新做 owner readback 和发布验收。
