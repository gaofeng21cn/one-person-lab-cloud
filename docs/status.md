## Fabric J0 READY Sandbox Qualification Producer (2026-10-18)

Against `79d81a4e` (main after #957), this change answers #952. Cloud fabric now
produces the J0 READY receipt the protected business qualification lane requires,
from a provider sandbox qualification run, instead of reading one from a producer
outside the protected job.

`tools/workspace-qualification-j0-ready.ts` reads the exact Candidate receipt and
the declared digest, refuses a digest the Candidate's own bytes do not produce,
reads the declared fabric sandbox (the same seven-field deployment binding the
protected lane validates, plus `authorityClass: "sandbox"` and `dedicated: true`),
and drives the new `runTencentTkeSandboxQualification` in
`tools/workspace-qualification-tencent-tke.ts` through the boundary module the
protected lane already loads. The run opens a dedicated workspace scope, checks
that the owner transport belongs to the deployment, reads the provider's own
health answer, and releases the scope in every case. `failed` and `skipped` are
counted from those observed checks; the caller cannot assert them. The boundary
receives the deployment binding, the derived `opl-j0-sandbox:<sha256>` operation
identity and a sandbox request of the exact shape
`{kind: "opl.workspace-qualification.j0-sandbox.v1", candidate: {receiptDigest,
productSha, productTree, cloudImageDigest}, authority: {mode, class, dedicated}}`,
so the external module needs one case for that kind beside its protected-lane
cases.

The emitted `opl.workspace-qualification.j0-ready.v2` receipt carries
`schemaVersion: 1`, `status` (`READY` only when every check passed),
`source: {sha, tree, cloudImageDigest, clean}`, `authority: {mode: "live",
class: "sandbox", dedicated: true, confirmed}`, `provider`, `failed` and
`skipped`. `confirmed` records that the provider answered the open, the transport
binding and the release. A v2 receipt is now bound to the exact Candidate through
`source.cloudImageDigest`: the shared validator refuses a v2 receipt validated
without its Candidate, or against another Candidate's SHA, tree or image digest.
The legacy `opl.local-workspace.j0-ready.v1` receipt keeps its `{sha, tree,
clean}` shape for the profiles that declare it, so the Local-Docker lane is
unchanged.

Transport remains a file, because the producer and the protected consumer run in
separate jobs on separate runners and the workflow still delivers protected
inputs from `$RUNNER_TEMP`. Cloud fabric writes the receipt with the consumer's
standard: an absolute path outside the repository, `O_CREAT | O_EXCL | O_NOFOLLOW`
creation at mode `0600`, one descriptor for the bytes, and the contract's 1 MiB
cap enforced before the write. `loadProtectedJ0ReadyReceipt` re-reads under the
same checks, now bounded to `J0_READY_MAX_BYTES`, and a well-formed receipt bound
to another Candidate is refused as `external_prerequisite_absent` while a
malformed, non-confirmed, non-`sandbox`, non-`live`, non-dedicated or non-zero
`failed`/`skipped` receipt keeps `j0_ready_receipt_invalid`. The workflow's jq
gate is unchanged and remains weaker than the loader, which is the authority; no
workflow, profile, deploy manifest or cluster state is changed.

## Workspace Managed-Key Lifecycle Source Wiring (2026-10-18)

Against `f966aa63` this change gives Gateway Integration the Cloud owner route
for one reversible managed-key transition and makes Workspace closure ask it to
disable the exact live binding. `DisableManagedKey`, `EnableManagedKey` and

## Workspace Lifecycle Triggers For The Managed Key (2026-10-18)

Against `79d81a4e` this change gives the extracted Workspace owner the two
remaining lifecycle triggers and the authorized recovery issue #868 names. The
owner already stored a `suspended` standing, the confirmed paid period, the
`subscriptions_expiry` index and the contract's `provider_suspend` and
`provider_resume` stages, but nothing ever advanced them.

Suspension is committed as this owner's own operation (`suspend_workspace`) and
closes the entitlement first. A confirmed paid period that ended without a
confirmed successor, or a Fabric readback that confirms the original resource set
absent, sets the Workspace status to `suspended`, which the owner's own
`ReadWorkspaceAccess` already refuses to Serve. Only then does the event ask
Gateway Integration to disable the exact live binding it resolves from the same
confirmed records the deletion closeout uses. Recovery (`resume_workspace`) reads
the Gateway's authoritative state first, re-enables that one binding, and
restores the Workspace only after the binding is confirmed readable again. That
last read matters now that a disabled binding refuses the key read every same-key
model update depends on: a restored Workspace never assumes its credential works. Both
events run under the original launch's accepted grant and its own tenant scope,
name one opaque binding, and record `confirmed`, `rejected`, `unknown` or
`not_applicable` under their own operation identity with the idempotency key
`<operation>:apply_managed_key_lifecycle`.

The triggers can fire on one Workspace at the same time. They serialize on one
advisory lock and one open event per kind, so the binding receives one effect. A
lost answer is settled by reading the Gateway's state before any second command,
and a revoked binding stays terminal in both directions without a replacement key
being issued. The production Sub2API adapter still answers `codes.Unimplemented`
for disable, enable and state readback, so this source records the refusal on the
event, keeps the Workspace suspended, and never converts that refusal into a
disabled key; deleting and refunding the same Workspace still completes on its
own evidence.

Local focused verification at this revision executes 69 package tests (107 with
subtests) with zero failures, skips or TODOs against the isolated PostgreSQL
fixture:

```sh

  OPL_OWNER_MIGRATION_TEST_ADMIN_DSN=postgres://... \

```

The new PostgreSQL checks drive the real owner transitions: an expired confirmed
term suspends before the key is named and disables exactly one binding under the
launch grant; a Fabric-confirmed resource loss suspends through the same route; a

after the readback; a lost answer is recovered by reading the authoritative state
without a second effect; two concurrent triggers produce one event, one step and
one effect; a revoked binding is neither disabled nor re-enabled and leaves the
Workspace suspended; and a refused key closeout still allows the Workspace's
deletion and refund to complete. Remaining: the approved Sub2API
disable/enable/state-readback endpoint, the retained Control Plane suspension and
expiry callers that must delegate here instead of writing their own Workspace
status, and a customer-visible closeout readback. These source checks do not establish the historical #868 runtime acceptance.

## Cloud Customer Readback Usage And Fee Coverage (2026-10-18)

Against `79fd6d5b`, this change extends the protected `customer_reads` producer
`tools/cloud-business-readback.ts` so one authenticated CloudIdentity session
asserts the four customer reads issue #840 names: wallet, usage summary, fee
records and announcements. The previous checks covered wallet and announcements
only, so a deployed origin could reject `GET /api/v2/usage/summary?period=month`
and `GET /api/v2/legacy-billing/receipts?limit=20` with 401 and still receive
`customer_reads_verified`. A fixture that answers a real HTTP 401 on either route
now blocks the receipt, even when the response body would satisfy that route's
shape check, so only the status gate can block it; the pre-change producer
returned `customer_reads_verified` for the same fixture. A separate fixture keeps
a 200 error body, which fails the shape check rather than the status gate. The
usage check requires the Gateway owner's canonical non-negative int64 strings.
The fee-record check requires the `ledger` source envelope; a 404 blocks the
receipt, because the BFF writes one generic owner-not-found both for a customer

## Current Source Baseline

The current source contains the target owner modules and the retained
migration source in one repository:

- Console UI/BFF provides the browser surface and typed owner aggregation.
- CloudIdentity/Tenant and Gateway Integration are separate data owners in one
  deployment unit.
- Capability, Build, Runtime Control, Workspace, Resource Catalog and Serve
  have their own owner processes and databases.
- Fabric owns provider resources and Secret bindings; Ledger owns receipts and
  reconciliation.
- Control Plane remains a migration source for callers that have not moved. It
  is not a second target writer.

The current product selection is a strict union:

- **Default OPL App**: an approved Runtime Release and its declared built-in UI.
  It does not invent a Package, BuildJob or CapabilityVersion.
- **Custom Agent**: an admitted Package, an approved Runtime Release and a
  compatible independent WebUI, fixed into one immutable Build output.

Workspace owns entitlement, model-configuration intent and target
authorization. Serve owns the current deployment, readiness, applied runtime
configuration and access route. Fabric never deploys the Agent OCI, Gateway
never owns Agent lifecycle, and Ledger never authorizes continuation.
