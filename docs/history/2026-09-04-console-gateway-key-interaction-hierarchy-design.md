# Console Gateway Key 交互层级设计 UX-03D-B

Date: 2026-09-04

State: proposed design record

## 目标与边界

UX-03D-B 把 Gateway Key 页面现状审计转换为可实现的交互层级。它只定义客户如何先看到结果、再执行高频动作、最后进入筛选和技术细节；不改变已经跑通的 Gateway 业务链路、API、DTO、权限、状态所有者或敏感值生命周期。

页面业务结果保持不变：

```text
进入 OPL Gateway
→ 查看当前 API Key
→ 判断状态、额度、有效期和最近使用
→ 显示/复制或打开使用说明
→ 必要时管理、维护或删除
```

所有浏览器请求仍只能经过 Control Plane；Sub2API 仍是 Gateway、Wallet、Key、Usage 的内部权威。

## 输入证据

- UX-03D-A 审计：`docs/history/2026-09-04-console-gateway-key-ui-audit.md`
- 审计提交：`461d4798 docs(console): audit gateway key page`
- 运行时视口：桌面 `1280×900`，移动 `390×844`
- 关键事实：移动端第一条 Key 约从 `y=784` 才开始，操作栏约在 `y=1113`；筛选器占据首屏主要空间；当前 7 个操作均为同级图标。

## 方案比较

### 方案 A：结果优先 + 筛选折叠 + 低频操作分组（推荐）

移动端先展示当前 Key，搜索/排序/分页放进一个默认关闭的“筛选与排序”区域；查看和使用动作保持直接可见，管理、维护和删除进入命名明确的“更多操作”。桌面保留高密度表格，但用视觉分组区分高频、维护和危险操作。

优点：直接修复审计中的两个 P1，保留当前能力和桌面效率，用户不需要切换页面模式。代价：需要重新组织现有 JSX/CSS，并为菜单或分组补充键盘和焦点行为。

### 方案 B：把 Key 列表和筛选拆为两个 Tab

“API 密钥”和“筛选条件”分别成为两个页面状态。

优点：首屏更干净。代价：查看结果和调整筛选需要来回切换，增加记忆负担；对只有一条或少量 Key 的当前业务没有必要，也会引入额外导航状态。因此不采用。

### 方案 C：保留当前顺序，只压缩控件和字体

优点：代码改动少。代价：筛选仍然先于结果，无法解决移动端核心任务被推到首屏之外的问题；压缩字号和间距还会损害可读性。因此不采用。

## 交互层级

### L0：页面身份

- 顶层身份：`OPL Gateway`
- 页面标题：`API 密钥`
- 局部导航仍为：`服务信息`、`用量`、`API 密钥`
- Endpoint 是调用前置事实，保留显示和复制，但不与 Key 结果争夺主视觉。

### L1：核心结果与主动作

- 首屏首先回答：当前有哪些 Key、状态是什么、额度用了多少、何时到期、最近何时使用。
- `创建 API 密钥` 是页面级主动作，保留在标题区域并使用主按钮样式。
- 有 Key 时，第一条当前 Key 及其状态必须在移动端首屏可见；无 Key 时，空状态和创建入口必须直接可见。
- 对每条 Key，`显示/隐藏 API 密钥` 和 `使用说明` 是直接可达的高频动作。

### L2：日常管理

- `编辑`
- `启用/停用`

这些动作影响 Key 的日常可用状态或配置，但不是用户每次进入页面都要执行的动作。

### L3：维护操作

- `重置配额用量`
- `重置消费限额用量`

这两项保留独立语义，不合并为一个含义不清的“重置”。它们属于维护层，不能与查看动作使用相同的视觉权重。

### L4：高风险操作

- `删除`

删除保持独立的危险样式、确认对话框和现有回读/幂等语义。不能因为折叠操作而变成无确认的一键动作。

### L5：辅助与技术层

- 搜索、状态筛选、排序、顺序、每页、服务分组筛选、查询、分页
- Endpoint 复制、刷新
- `技术详情`

这些控件和字段服务于查找、诊断或配置，不应遮挡当前 Key 结果。技术详情和敏感值继续默认关闭/隐藏。

## 桌面交互布局

桌面保持高效表格，不引入新的页面或服务：

```text
页面身份与 Endpoint（辅助） → 创建（主动作）
→ Key 结果表（主区域）
→ 每行：名称/状态/额度/有效期/最近使用
→ 每行操作：查看与使用 | 日常管理 | 维护 | 删除
→ 分页
```

筛选与排序可以在桌面保持单行工具栏，但视觉上放在结果区域的辅助层，不得与页面标题或创建按钮同权。操作列使用现有图标库和 ARIA 名称；低频动作可以进入命名为 `更多操作` 的菜单，但菜单项必须保留可见中文名称和当前权限状态。

## 移动交互布局

移动端采用结果优先顺序：

```text
Shell + Gateway tabs
→ API 密钥标题
→ Endpoint（紧凑辅助信息）
→ 创建 API 密钥（主动作）
→ 第一条 Key 卡片：名称、状态、额度、有效期、最近使用
→ 查看/使用动作
→ 更多操作
→ 筛选与排序（默认关闭）
→ 分页
```

具体规则：

1. 首屏不再纵向堆叠搜索、状态、排序、顺序和每页控件。
2. `筛选与排序` 是一个明确的可聚焦控制，默认关闭；打开后承载现有搜索、状态、排序、顺序、每页和技术筛选，不删除任何查询能力。
3. 当前查询状态在筛选区关闭后仍保留，关闭只收起呈现，不重置查询，也不产生额外业务请求。
4. Key 卡片内直接显示查看/使用动作；`更多操作` 菜单承载编辑、启停、两种重置和删除，并按“管理 → 维护 → 删除”分段。
5. 任何操作都保持至少 `44×44px` 触控目标、可见焦点和键盘可达；菜单打开时焦点进入菜单，关闭后返回触发控件。
6. 不使用横向滚动承载操作。卡片宽度必须适应 `390×844`，技术详情继续在卡片内折叠。

## 受保护 Workspace Key

Workspace 系统 Key 的限制仍由服务端 DTO 的 `kind`、`manageable`、`deletable` 决定。页面不创建第二个权限来源。

- 查看/使用动作仍可达。
- 编辑、启停、两种重置和删除继续表现为不可用或明确不可执行，并保留现有解释文案。
- `更多操作` 不得通过视觉折叠伪装成可执行；用户应能知道这些动作受系统 Key 限制。

## 状态、错误和敏感值

- Loading、empty、unavailable、partial reference failure、permission 和 busy 状态保持现有 `SourceState`/错误处理，不把不可用转换为零或空成功。
- 创建、编辑、启停、重置和删除继续使用现有 CSRF、Idempotency-Key、权威回读和错误文案。
- 显示 API 密钥前必须显式点击；完整值不进入初始 DOM、localStorage、sessionStorage 或 URL。
- Reveal 仍通过现有 `POST /api/gateway/keys/{keyId}/reveal`，页面内存保存，60 秒自动隐藏；使用说明复用当前 reveal 值的行为不变。
- 任何 UI 分组不改变请求数量、请求顺序的业务要求或源状态所有者。

## UX-03D-C 实现验收标准

### 移动端

- `390×844` 首屏可看到第一条 Key 的名称和状态；有 Key 时至少能直接发现查看/使用动作。
- 搜索、状态、排序、顺序、每页和技术筛选默认收起到一个“筛选与排序”控制。
- “更多操作”明确列出编辑、启停、两种重置和删除；删除单独危险分段并保留确认。
- 卡片无横向溢出，键盘和触摸均可达，菜单焦点行为正确。

### 桌面端

- `1280×900` 保持表格效率和分页可达。
- 查看/使用、日常管理、维护、删除在操作列中有可理解的视觉分组。
- 筛选工具栏仍可直接使用，但不压过 Key 结果和创建主动作。

### 共同验收

- 创建、读取、Reveal、编辑、启停、两种重置、删除和分页仍调用现有 Control Plane adapter；不新增 Gateway/Key/Wallet/Usage API。
- 技术详情默认关闭，Key 默认隐藏，Reveal 生命周期仍为 60 秒。
- Workspace 系统 Key 限制不变。
- 无 page error、Console error、外部请求和移动端横向溢出。
- 业务链路、DTO、权限、状态来源、Sub2API 权威和后端持久化不变。
